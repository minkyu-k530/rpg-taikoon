## 2026-11-23 — `docs/game-design` — 기획 확정 (PR #1)

### 한 일

- 개발 일지 / 트러블슈팅 문서 체계 생성

### 결정한 것

| 항목 | 결정 | 버린 선택지와 이유 |
|---|---|---|
| 플랫폼 | **웹 (React + Three.js)** | *Unity 모바일*: 광고 수익은 가장 크지만 씬·프리팹이 바이너리라 AI가 작업할 수 없고 첫 플레이까지 3~4주. 재미 검증 전에 수익 축을 고르면 3개월을 날린다<br>*Unity WebGL*: 로딩 20~40MB, iOS Safari 메모리 이슈 |
| 가게 | **분식 포장마차** (붕어빵 중심) | *붕어빵 단독*: 겨울 계절감에 갇혀 메뉴 확장 축이 막힘 |
| 배경 | **판교 운중천 산책로** | *일반 골목*: 특징이 없음. 판교는 본인 생활권이라 레퍼런스 사진을 직접 찍을 수 있고, 켜진 오피스 창으로 "야근"을 배경만으로 설명 가능 |
| 에셋 | **무료 + Mixamo** | *유료 Synty($40~60)*: 스타일 통일은 쉽지만 비용 발생. 대신 공용 토온 셰이더 + 팔레트 12색으로 통일성을 강제하기로 함 |
| 통화 | 원(₩) 1종 | *프리미엄 화폐*: 잔잔함과 충돌하고 설계 복잡도만 늘어남 |

### 핵심 판단
방치형 타이쿤은 레드오션이다. 수치 성장이 아니라 **단골 이야기 해금**이 유일한 차별 축이고, 업그레이드는 그걸 여는 열쇠로만 존재한다.

## 2026-11-23 — `feat/web-prototype` — 1~2주차 회색 박스 (PR #2)

### 한 일
Vite + React + Three.js로 프로토타입을 만들고 브라우저에서 하루를 끝까지 돌렸다.

- 주민 상태머신: `walk → browse → queue → serve → eat → leave`
- 붕어빵 굽기 / 뒤집기 창 / 진열 / 판매 / 하루 정산 / 업그레이드 4종
- 밤 조명, 건너편 오피스의 켜진 창, 하천, 전경 소품

### 측정한 하루 (성실히 뒤집었을 때)

| 항목 | 값 |
|---|---|
| 손님 | 16명 |
| 판매 | 18개 |
| 매출 | 18,000원 |
| 재료비 | 6,300원 |
| **순이익** | **11,700원** |
| 못 판 손님 | 0명 |

뒤집기를 한 번도 안 하면 전부 700원에 팔려 하루 매출이 12,600원으로 떨어진다.
**뒤집기라는 단 하나의 조작이 매출을 30% 움직인다** — 조작이 선택이면서도 의미가 있어야 한다는 설계 원칙(GDD 4장 3번)이 수치로 성립했다.

### 결정한 것

| 항목 | 결정 | 버린 선택지와 이유 |
|---|---|---|
| 상태 관리 | 클래스 하나 (`sim.ts`) + 10Hz 스냅샷 | *zustand 등 라이브러리*: 이 규모에 불필요. 매 프레임 갱신은 어차피 `useFrame`에서 Three.js 객체를 직접 건드려야 하므로 스토어가 할 일이 없다 |
| 주민 렌더링 | 상의·하의·머리·팔다리를 나눈 박스 | *캡슐 하나*: 20명이 각기 달라 보이는지를 지금 검증해야 하는데 캡슐로는 판단이 안 된다 |
| 어묵탕 | 조작 없이 상시 판매되는 메뉴로 설계 | 손을 놓아도 가게가 돌아간다는 보장이 필요했다. 잔잔함의 기계적 근거 |
| 영업 길이 | 150초 (GDD는 6~8분) | 프로토타입 단계에서는 하루를 여러 번 돌려봐야 해서 짧게. 출시 때 되돌린다 |
| 보행 범위 | X ±11m | 처음엔 ±24m로 잡았는데 카메라 화각 밖이라 사람이 흩어져 보였다. **화면에 안 보이는 곳까지 시뮬레이션할 이유가 없다** |

### 겪은 문제
TS-002(포트 충돌), TS-003(InstancedMesh 컬링), TS-004(줄서기 교착) — `TROUBLESHOOTING.md` 참조.
셋 다 **에러를 던지지 않는 종류의 버그**였다. 그래서 개발 모드에 `window.__sim` 핸들을 열어 두었다.
