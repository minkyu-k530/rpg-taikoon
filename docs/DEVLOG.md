## 2026-11-23 — `feat/web-prototype` — 1~2주차 회색 박스 (PR #2)

### 한 일
Vite + React + Three.js로 프로토타입을 만들고 브라우저에서 하루를 끝까지 돌렸다.

- 주민 상태머신: `walk → browse → queue → serve → eat → leave`
- 붕어빵 굽기 / 뒤집기 창 / 진열 / 판매 / 하루 정산 / 업그레이드 4종
- 밤 조명, 건너편 오피스의 켜진 창, 하천, 전경 소품

### 측정한 하루 (성실히 뒤집었을 때)

| 항목 | 값 |
|---|---|
| 손님 | 16명 |
| 판매 | 18개 |
| 매출 | 18,000원 |
| 재료비 | 6,300원 |
| **순이익** | **11,700원** |
| 못 판 손님 | 0명 |

뒤집기를 한 번도 안 하면 전부 700원에 팔려 하루 매출이 12,600원으로 떨어진다.
**뒤집기라는 단 하나의 조작이 매출을 30% 움직인다** — 조작이 선택이면서도 의미가 있어야 한다는 설계 원칙(GDD 4장 3번)이 수치로 성립했다.

### 결정한 것

| 항목 | 결정 | 버린 선택지와 이유 |
|---|---|---|
| 상태 관리 | 클래스 하나 (`sim.ts`) + 10Hz 스냅샷 | *zustand 등 라이브러리*: 이 규모에 불필요. 매 프레임 갱신은 어차피 `useFrame`에서 Three.js 객체를 직접 건드려야 하므로 스토어가 할 일이 없다 |
| 주민 렌더링 | 상의·하의·머리·팔다리를 나눈 박스 | *캡슐 하나*: 20명이 각기 달라 보이는지를 지금 검증해야 하는데 캡슐로는 판단이 안 된다 |
| 어묵탕 | 조작 없이 상시 판매되는 메뉴로 설계 | 손을 놓아도 가게가 돌아간다는 보장이 필요했다. 잔잔함의 기계적 근거 |
| 영업 길이 | 150초 (GDD는 6~8분) | 프로토타입 단계에서는 하루를 여러 번 돌려봐야 해서 짧게. 출시 때 되돌린다 |
| 보행 범위 | X ±11m | 처음엔 ±24m로 잡았는데 카메라 화각 밖이라 사람이 흩어져 보였다. **화면에 안 보이는 곳까지 시뮬레이션할 이유가 없다** |

### 겪은 문제
TS-002(포트 충돌), TS-003(InstancedMesh 컬링), TS-004(줄서기 교착) — `TROUBLESHOOTING.md` 참조.
셋 다 **에러를 던지지 않는 종류의 버그**였다. 그래서 개발 모드에 `window.__sim` 핸들을 열어 두었다.

### 아직 아닌 것
- 캐릭터 에셋 (3~4주차)
- 단골·호감도 (5~8주차). 지금은 손님이 매번 처음 보는 사람이다
- 저장, 사운드, 날씨

### 다음
3~4주차: 무료 에셋 + Mixamo 파이프라인. 합격 기준은 "20명이 각기 달라 보이는가".

## 2026-11-23 — `feat/regulars` — 단골 시스템과 저장 (PR #3)

### 한 일
손님을 **매번 새로 뽑는 난수 인형에서 고정 명부로** 바꿨다. 이게 이 게임의 차별 축이다.

- `src/game/residents.ts` — 단골 8명(이름·외형·대사 5줄·에피소드) + 이름 없는 행인 12명
- 호감도 4단계: 3회 이름 표시 → 7회 단골(대사 1줄) → 15회 아는 사이(3줄) → 30회 가족 같은(에피소드)
- 머리 위 이름표와 말풍선 (캔버스 텍스처 스프라이트, 문장당 텍스처 1개 캐시)
- 단골 도감 UI
- localStorage 저장·복원 (날짜·돈·업그레이드·방문 횟수)

### 실측: 12일 연속 플레이 (게임 내 시뮬레이션 고속 실행)

| 날 | 해금 |
|---|---|
| 2 | 정하람 눈에 익음 |
| 3 | 최영숙·박승우·윤도경 눈에 익음 |
| 5 | 윤도경·정하람 단골 |
| 8 | 박승우 단골 |
| 11 | 윤도경 아는 사이 |
| 12 | 정하람 아는 사이 |

12일차에 8명 전원과 면식. **"가족 같은"(30회)은 22~25일차 예상.**
하루 순이익은 1만 2천 원 안팎에서 평평했다 — 업그레이드를 안 샀기 때문이고, 의도대로다.

### 결정한 것

| 항목 | 결정 | 버린 선택지와 이유 |
|---|---|---|
| 손님 생성 | 고정 명부 20명에서 가중 추첨, 거리에 이미 있는 사람은 제외 | *완전 난수 생성*: 같은 사람이 다시 온다는 느낌이 안 난다. 단골이라는 개념 자체가 성립 못 함 |
| 단골 보상 | 단계당 구매 확률 +8%p | *할인·팁 같은 돈 보상*: 관계를 거래로 만든다. 자주 온다는 것 자체가 보상이어야 함 |
| 이름표 | 3D 스프라이트(캔버스 텍스처) | *DOM 오버레이*: 매 프레임 3D→화면 좌표 투영이 필요하고 사람이 늘수록 레이아웃이 터진다 |
| 외형 | 모자·머리·가방 6종 조합을 주민별로 **고정** | *매번 랜덤*: 같은 사람인 걸 알아볼 수 없다. 단골 시스템이 무의미해진다 |
| 저장 | localStorage + 버전 번호 | 스키마가 바뀌면 옛 저장은 조용히 버린다. 프로토타입 단계에서 마이그레이션은 과하다 |

### 배운 것
`as const`로 선언한 설정값을 클래스 필드 초기값에 쓰면 그 필드가 **리터럴 타입으로 고정**된다
(`money = CONFIG.startMoney` → 타입이 `20000`). 저장 복원에서 `number`를 대입할 때 터졌다.
설정이 `as const`면 가변 필드는 `money: number = ...`로 타입을 명시한다.

## 2026-11-23 — `feat/weather` — 날씨와 수요 탄력 (PR #4)

### 한 일
맑음 / 눈 / 비 세 날씨. 눈과 비는 입자로 그리고, 비 오는 날은 바닥이 젖어 가로등이 번진다.
마감 화면에 **내일 날씨 예보**를 띄워 다음 날을 준비하게 했다.

| 날씨 | 유입 | 구매 확률 | 체류 |
|---|---|---|---|
| 맑음 | ×1 | ×1 | ×1 |
| 눈 | ×0.95 | ×1.5 | ×1.2 |
| 비 | ×0.82 | ×1.3 | ×1.4 |

### 실측 (날씨·설비 조합마다 하루를 8번 돌려 평균)

| 설비 | 맑음 | 눈 | 비 |
|---|---|---|---|
| 틀 2개 | 17,750원 (부족 10개) | 17,625원 (**부족 12개**) | 16,000원 (부족 5개) |
| 틀 6개 + 어묵탕 | 28,250원 | **32,750원 (+16%)** | 27,000원 (−4%) |

### 여기서 나온 설계 발견
**날씨는 공급이 수요를 따라갈 수 있을 때부터 매출로 바뀐다.**

틀이 2개뿐인 초반에는 눈이 와도 매출이 안 오른다. 이미 만드는 족족 팔리기 때문이다.
대신 "재고가 없어 못 판 개수"가 10개 → 12개로 오른다. 즉 초반의 눈은 **돈이 아니라 아쉬움으로 돌아오고**,
그 아쉬움이 틀을 늘릴 이유가 된다. 설비를 갖춘 뒤에야 눈이 +16% 매출로 바뀐다.

이건 설계하고 만든 게 아니라 **수치를 재다가 발견했다.** 그래서 마감 화면에 "재고가 없어 못 판 개수"를 새로 넣었다.
이 숫자가 없으면 플레이어는 눈 오는 날 무슨 일이 일어났는지 알 수 없다.

### 결정한 것

| 항목 | 결정 | 버린 선택지와 이유 |
|---|---|---|
| 비의 성격 | 유입 ×0.82, 구매 ×1.3, 체류 ×1.4 | 처음엔 유입 ×0.7, 구매 ×1.1로 잡았더니 매출이 **−33%**. 실패가 없어야 하는 게임에서 날씨가 벌점이 됐다. 비는 "손해 보는 날"이 아니라 **"사람은 적고 오래 머무는 날"** 이어야 한다 |
| 입자 | React 바깥에서 BufferAttribute 직접 갱신 | 눈 900개·비 1400개를 React로 돌리면 즉사한다 |
| 예보 | 마감 화면에 내일 날씨 표시 | 잔잔한 게임에도 **다음 날을 기대할 이유**는 필요하다. 눈 예보를 보면 오늘 틀을 사게 된다 |

### 다음
소리. 기름 끓는 소리, 물소리, 눈 오는 날의 먹먹함. 잔잔함의 나머지 절반이다.
