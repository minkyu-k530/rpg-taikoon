# 운중천 분식 (가제)

판교 운중천 산책로 옆 분식 포장마차. 실패도 시간 압박도 없고, 지나가던 사람이 단골이 되어 가는 걸 지켜보는 잔잔한 가게 타이쿤.

기획서는 [`docs/GDD.md`](docs/GDD.md), 작업 기록은 [`docs/DEVLOG.md`](docs/DEVLOG.md), 에러·버그 기록은 [`docs/TROUBLESHOOTING.md`](docs/TROUBLESHOOTING.md).

## 목표

1. 만드는 사람 본인의 재미
2. 출시와 수익
3. 위 둘의 결과로 따라오는 취업 포트폴리오

## 지금 상태

**1~2주차 회색 박스 프로토타입 완료.** 전부 기본 도형이고 캐릭터 에셋은 아직 없다.

동작하는 것:

- 주민 20명 안팎이 산책로를 각자 다른 속도로 걷는다. 서로 비껴가고, 멈춰서 구경하고, 줄을 서고, 사서 먹고 간다
- 붕어빵을 굽고 → 뒤집기 창에 탭하면 제값, 놓치면 바삭한 붕어빵으로 싸게 팔린다 (실패 없음)
- 진열대 재고가 떨어지면 손님은 화내지 않고 기다리다 조용히 간다
- 하루(150초) 영업 → 마감 정산 → 업그레이드(틀·간판·온풍기·어묵탕) → 다음 날

측정한 하루(성실히 뒤집었을 때): 손님 16명, 18개 판매, 매출 18,000원, 재료비 6,300원, **순이익 11,700원**, 못 판 손님 0명.

## 실행

```sh
npm install
npm run dev     # http://localhost:5180
```

| 스크립트 | 용도 |
|---|---|
| `npm run dev` | 개발 서버 |
| `npm run build` | 타입체크 + 프로덕션 빌드 |
| `npm run typecheck` | 타입만 검사 |

개발 모드에서는 브라우저 콘솔에 `__sim`으로 시뮬레이션 상태가 노출된다.

```js
__sim.villagers.length   // 거리에 있는 사람 수
__sim.stats              // 오늘 매출/판매/손님
__sim.dayTime = 149      // 마감 화면으로 점프
```

## 기술 선택

| | 선택 | 이유 |
|---|---|---|
| 플랫폼 | 웹 | 첫 플레이까지 당일. 재미 검증 후 모바일 이식 |
| 렌더링 | Three.js + @react-three/fiber | 전부 텍스트 코드라 AI가 끝까지 작성·검증 가능 |
| 상태 | 클래스 하나 (`src/game/sim.ts`) | 상태 라이브러리 없이 충분. React는 10Hz 스냅샷만 받는다 |

Unity를 쓰지 않은 이유는 [`docs/GDD.md` 1-1](docs/GDD.md)에 적어 두었다.

## 구조

```
src/
  game/
    config.ts       밸런싱 수치와 씬 좌표계. 숫자는 전부 여기
    sim.ts          시뮬레이션. React·Three.js 의존 없음
    useSim.ts       React 다리. UI는 10Hz 스냅샷만 본다
  scene/
    Environment.tsx 산책로·하천·난간·가로등·건너편 오피스
    Stall.tsx       포장마차와 붕어빵 틀
    Crowd.tsx       주민 렌더링. 위치는 매 프레임 sim에서 직접 읽는다
  ui/HUD.tsx        상단 정보, 뒤집기 버튼, 마감 정산
```

**성능 규칙 하나: 매 프레임 바뀌는 값은 React state에 넣지 않는다.** 위치·색은 `useFrame`에서 Three.js 객체를 직접 건드리고, React는 10Hz 스냅샷만 리렌더한다.

## 잔잔함의 기준

분위기는 모델 품질이 아니라 주민 행동에서 나온다.

- 주민마다 걷는 속도와 보폭이 조금씩 다르다
- 목적지 앞에서 서성이고, 구경하고, 고개를 돌린다
- 실패나 시간 압박이 없다

프로토타입 합격 기준은 하나다. **그 화면을 10분 동안 멍하니 보고 싶은가.** 아니라면 그래픽을 입히기 전에 주민 행동을 고친다.

- 결정과 **버린 선택지**는 `docs/DEVLOG.md`에, 에러·버그는 `docs/TROUBLESHOOTING.md`에 남긴다.
